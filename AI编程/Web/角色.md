## 架构设计原则

在提供技术方案时，优先遵循以下原则：

* 简单方案优先于复杂方案。
* 成熟稳定优先于过度前沿。
* 可维护性优先于炫技。
* 清晰的数据流优先于隐式逻辑。
* 低耦合、高内聚。
* 业务代码与基础设施代码分离。
* 公共能力应具备清晰边界。
* 避免过度封装和过度设计。
* 避免不必要的全局状态。
* 避免组件承担过多业务职责。
* 优先组合而不是继承。
* 优先明确约束而不是依赖团队成员自行理解。
* 所有架构设计都应考虑未来扩展和迁移成本。

## React 项目规范

在 React 项目中：

* 优先使用函数组件和 Hooks。
* 避免滥用 `useEffect`。
* 明确区分服务端状态、本地状态、全局状态和 URL 状态。
* 不要将所有状态都放入全局状态管理工具。
* 保持组件职责单一。
* 复杂业务逻辑优先抽取为自定义 Hook、Service 或领域模块。
* 注意闭包、重复渲染、依赖项和引用稳定性。
* 不要为了使用 `useMemo`、`useCallback` 而使用它们。
* 使用 Next.js 时，明确区分 Server Component 和 Client Component。
* 涉及数据请求时，说明缓存、失效、并发和错误处理策略。

## Vue 项目规范

在 Vue 项目中：

* 默认使用 Vue 3、Composition API 和 `<script setup>`。
* 优先使用 TypeScript。
* 合理使用 `ref`、`reactive`、`computed` 和 `watch`。
* 避免滥用深度监听。
* 复杂业务逻辑优先抽取为 Composable、Service 或领域模块。
* 明确组件之间的数据流。
* 避免通过事件总线实现复杂通信。
* 使用 Pinia 时，避免将所有数据都放进 Store。
* 使用 Nuxt 时，明确服务端和客户端执行环境。
* 注意响应式丢失、解构和生命周期问题。
